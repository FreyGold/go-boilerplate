How your Go job system works

This guide starts with the smallest idea. It then connects each part to your saved code. The final sections show what works and what is still missing.

1. Core idea

A queue separates the time when your application requests work from the time when a worker does the work.

ApplicationRequests a welcome email.
→
TaskDescribes the work.
→
RedisStores the task.
→
WorkerReads the task.
→
HandlerSends the email.

The task contains data. It does not contain Go functions. The worker already has the handler code. The task type tells the worker which handler to call.

Remember this sentence: The producer writes a task to Redis. A worker reads the task. A handler does the work and returns a result.

2. The exact handoff point

NewWelcomeEmailTask does not move work to the queue. It only creates a Go value in local memory.

task, err := job.NewWelcomeEmailTask(
    user.Email,
    user.FirstName,
)

The handoff occurs when Enqueue succeeds:

_, err = jobService.Client.Enqueue(task)
HTTP request
Save user Create task Enqueue task Return response
Redis
Store task Wait for worker
Worker
Read task Call handler Send email

After Enqueue succeeds, the HTTP request does not need to send the email. Redis holds the task after the request ends.

3. The building blocks

Each part has one main responsibility.

Task

It describes one unit of work.

Your task has a type, a JSON payload, a queue, a retry limit, and a timeout.

Producer

It creates and enqueues tasks.

Your Asynq client is the producer tool.

Broker

It stores tasks between the producer and worker.

Your broker is Redis.

Worker

It checks Redis for available tasks.

Your Asynq server manages the workers.

Router

It maps a task type to a handler.

Your router is asynq.ServeMux.

Handler

It converts task data into an action.

Your handler decodes JSON and calls the email client.

Email client

It renders the template and calls Resend.

It does not need to know about Redis or Asynq.

5. Startup flow and task flow are different

Startup flow

This flow runs once when the program starts.

  1. Load configuration.
  2. Create the logger.
  3. Call NewJobService.
  4. Call InitHandlers.
  5. Call Start.
  6. Call Stop during shutdown.

Task flow

This flow runs for each welcome email.

  1. Create the task.
  2. Enqueue the task.
  3. Read it from Redis.
  4. Route it to the handler.
  5. Decode the payload.
  6. Send the email.
  7. Return a result.

Important: NewJobService builds the queue system. NewWelcomeEmailTask creates one item that moves through the system.

6. Does the work leave the main application?

It depends on where you run the Asynq server.

Same process

One Go processRuns the API and Asynq server.
→
HTTP goroutineEnqueues and returns.
+
Worker goroutineReads and handles the task.

The work leaves the HTTP request. It does not leave the Go process. The API and worker share CPU and memory.

Separate processes

API processCreates and enqueues tasks.
→
RedisStores shared tasks.
→
Worker processRuns the server and handlers.

Now the work leaves the API process. You can deploy and scale the API and worker separately.

Your JobService contains both the client and server. This design can run both roles in one process. You can split these roles later if you need process isolation.

7. Errors, retries, and queue priority

The handler return value tells Asynq what happened.

return nil
→
Complete
The task succeeded.
return err
→
Retry
Asynq schedules another attempt if retries remain.
All retries fail
→
Archive
Asynq stops automatic attempts.
What does concurrency 10 mean?
One Asynq server can process at most ten tasks at the same time. It does not create ten queues.
What do queue weights 6, 3, and 1 mean?
The values are relative priorities. Asynq checks critical more often than default. It checks default more often than low. The values are not fixed worker counts.
Can one task run more than once?
Yes. A worker can finish the external action and fail before it records success. Asynq can then retry the task. Important handlers must be safe when they run more than once.

8. A good build order

Build from the real action to the application connection.

  1. Send one email without a queue. This proves that the template and Resend work.
  2. Add SendWelcomeEmail. Keep welcome-email choices in one method.
  3. Define the task type and payload. This creates the producer-worker contract.
  4. Create the task factory. Add JSON, queue, retry, and timeout settings.
  5. Create the handler. Convert task data into the email action.
  6. Create the Asynq client and server. Connect both to Redis.
  7. Register the handler. Map the task type to the handler.
  8. Connect application startup. Initialize, start, and stop the job service.
  9. Connect signup. Create and enqueue a task after user creation succeeds.

This order limits the number of unknown parts in each step.

Current design risks
  • emailClient is a package variable. A field on JobService would make the dependency clear.
  • The handler receives a context, but the Resend call does not use it. The timeout cannot cancel the full email operation.
  • The template path is relative. The program working directory controls where Go looks for the file.
  • The email client stores a logger, but the current email methods do not use it.

10. What you should learn

You do not need to memorize all Asynq calls. Learn the stable model first.

Remember

  • A task is data that describes work.
  • Enqueue is the handoff point.
  • Redis separates producer time from worker time.
  • The router selects a handler.
  • The handler returns success or failure.
  • A separate worker process gives process isolation.

Look up when needed

  • Exact Asynq constructor syntax.
  • Task option names.
  • Server configuration fields.
  • Resend request fields.
  • Deployment commands.

Practice method: Draw the flow. Explain each arrow. Then add one similar task, such as a password-reset email. Repetition will make the structure familiar.
