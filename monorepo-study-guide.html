The big picture

Your repository holds several related projects. Some run as programs. Some provide code or files to those programs. They do not all run inside Go.

Keep three connections separate. TypeScript packages can import code from each other. A browser can send an HTTP request to Go. Build tools can write files that Go later reads.

The arrows show different kinds of connections. The file exports and HTTP request are separate actions; they do not happen merely because the folders exist.

Where does the code run?

PlaceWhat runs there
Development terminalBun calls Turbo. Turbo starts Vite, the TypeScript watchers, and the email preview. These are development tools on your computer.
Web browserThe browser receives frontend files from Vite and runs the frontend JavaScript. It can send an HTTP request to the Go server.
Go processYour compiled Go program runs as its own process. It listens for HTTP requests and reads its own configuration and files.
Other servicesThe Go server connects to services such as the database and Redis using their configured addresses.

A port identifies a network endpoint on a computer. During development, Vite requests port 3000 and the email preview requests 3001. The Go port comes from backend configuration. The current Go router serves API and documentation routes; it does not serve the frontend app as its website.

What is a monorepo?

A repository is a place that holds files and their version history. A monorepo holds several related projects in one repository. Your Go server, web app, and shared TypeScript packages live together here.

What it gives you

One place to change related code. A frontend change and a shared schema change can be reviewed together. Workspace tools can find local packages by name.

What it does not give you

One language, one process, or automatic agreement between Go and TypeScript. A shared repository makes coordination easier; you still have to connect the pieces.

Connect it to Go

You already know that Go files form packages and that a Go module has a go.mod. The JavaScript side has packages too. A JavaScript package usually has a package.json. The shared word package is useful, but the two systems have different rules.

In this repository, apps/ groups applications and packages/ groups supporting packages. These names are conventions. The important part is how each tool is configured.

Packages, workspaces, and Bun

What is a package?

A JavaScript package is a unit of code with a name and a manifest. A package can be a runnable app, a reusable library, or a tool. The manifest can list dependencies and commands.

{
  "name": "@boilerplate/openapi",
  "scripts": { "dev": "..." },
  "dependencies": {
    "@boilerplate/zod": "workspace:*"
  }
}

This is a shortened example from packages/openapi/package.json. The name lets another package refer to it. The scripts section names commands. The dependency says that OpenAPI needs the local Zod workspace package.

What is a workspace?

A workspace is a package managed as part of the same repository. The root manifest uses apps/* and packages/* to find JavaScript packages in those directories. Bun links local packages so their names can be used in imports.

frontenddeclares the local OpenAPI package
→
@boilerplate/openapideclares the local Zod package
→
@boilerplate/zodexports schema code

The frontend also declares Zod directly. workspace:* means “use a matching local workspace package.” The @boilerplate/ prefix is a package scope: it groups package names. It is not a Go import path or a network URL.

apps/backend matches the folder pattern, but it has a go.mod rather than a JavaScript package.json. It is a Go module, not one of the four JavaScript packages in the Turbo output.

What does Bun do?

Bun is a JavaScript runtime and package manager. Here you use it to install workspace dependencies and run package scripts.

CommandWhat happens
bun installReads manifests, resolves and installs dependencies, links workspaces, and updates the lockfile when needed.
bun devRuns the root script named dev. That script calls Turbo.
bun run genRuns the current package's script named gen. Its meaning depends on the current directory.

dependencies lists packages used by the package. devDependencies lists tools used to develop or build it, such as typescript and wait-on. An installed script can find executable tools through node_modules/.bin.

A version such as ^5.8.3 is a range, not a single installed version. For this major version, it permits compatible 5.x releases below 6. The lockfile records the version actually selected. ~5.8.3 is a narrower range within 5.8.x.

Different packages can request different versions of the same dependency. Here the frontend requests Zod 4.x, while the shared Zod and OpenAPI packages request Zod 3.x. Read the manifest for the package you are studying.

What Turbo does

Turbo is a task runner for a monorepo. It finds workspace packages, reads their scripts, and runs matching tasks. It can also order tasks using the package dependency graph and reuse cached results when a task permits caching.

Yourun bun dev at the root
→
Bunreads the root dev script
→
Turboruns dev in applicable workspaces
→
Package scriptsstart Vite, compilers, and email preview

The root dev script is turbo run dev. Turbo finds a dev script in the frontend, Zod, OpenAPI, and emails packages. It does not create those scripts; each package defines its own.

Read turbo.json

"build": { "dependsOn": ["^build"] },
"dev":   { "cache": false, "persistent": true }

For build, ^build means run the build tasks of dependency packages first, when those tasks exist. The dev task is persistent because watchers and servers keep running. Its cache is disabled because development processes need to run.

The dev task has no dependsOn entry here. The package scripts use wait-on to wait for files. Do not confuse this file check with Turbo's build ordering.

Important: Turbo does not start your Go backend in this setup. Run Go separately. The root development command starts the four JavaScript workspace tasks.

TypeScript, source files, and builds

JavaScript runs in browsers and JavaScript runtimes. TypeScript adds a type system and tooling to JavaScript. Tools check or transform TypeScript into JavaScript that a runtime can use.

ItemIts job here
src/Human-edited source code.
dist/Generated output from a build. The shared packages emit JavaScript and declaration files here.
.ts / .tsxTypeScript files. TSX can contain JSX, the markup-like syntax used in React components.
.d.tsType declarations for consumers. They describe types; they do not run as program logic.
tscThe TypeScript compiler. tsc -w watches files for changes.
tsc-aliasRewrites configured path aliases in compiled output. It can also run in watch mode.
concurrentlyRuns the compiler watcher and alias watcher at the same time.
ViteServes the frontend during development and builds frontend assets for deployment.
ReactA library for composing the user interface from components.

exports in a package manifest specifies public entry points for package consumers. For example, Zod exposes its compiled dist/index.js and its types. This is similar in purpose to defining a public surface, although the rules differ from Go's exported names.

The frontend's vite.config.ts also maps @boilerplate/openapi and @boilerplate/zod to their source folders. Its @ alias points to frontend source. Vite's aliases affect how Vite resolves imports; the manifest's exports matters to other package consumers.

Follow a health request

This is the best example of how the languages meet. The TypeScript code describes an API. The Go server implements a route. The connection between them is an HTTP request and a JSON response.

SchemaZod describes the response shape
→
Contractts-rest declares GET /status
→
Frontend clientcan make an HTTP request
→
Go handlerchecks services and returns JSON

1. Zod describes the data

In packages/zod/src/health.ts, ZHealthResponse describes fields such as status, timestamp, and checks.database. The Redis check is optional. Zod schemas are runtime values: code can use them to inspect data. TypeScript types alone are removed when code is compiled.

// Simplified shape, based on ZHealthResponse
{
  status: "healthy",
  timestamp: "2025-08-06T12:00:00Z",
  environment: "local",
  checks: {
    database: { status: "healthy", response_time: "2ms" }
  }
}

2. The contract describes the route

packages/openapi/src/contracts/health.ts declares GET /status and associates its 200 response with ZHealthResponse. contracts/index.ts collects the health contract into apiContract.

3. Go implements the route

apps/backend/internal/router/system.go registers GET /status. The health handler checks the database, checks Redis when a client is present, and writes JSON. It can return 503 when the database check fails.

4. The frontend has a client

apps/frontend/src/api/index.ts imports apiContract and passes it to initClient. Its custom request function uses Axios. The current App.tsx only renders “Hello World”; it does not call this client yet.

Current differences to notice: the client builds API_URL + "/api" + path. For the contract path /status, that is /api/status. Go registers /status. The contract declares only a 200 response, while the Go handler can also return 503. These pieces need to agree before this example can be relied on end to end.

The frontend code defaults VITE_API_URL to http://localhost:3000. Check the actual backend address and any proxy before making a request. The frontend and backend are separate origins when their ports differ, so the Go CORS configuration also matters.

The Go compiler does not read the Zod schema. Changing a TypeScript contract does not automatically change a Go handler. Keep the path, status codes, and JSON shape in agreement, and test the boundary.

How OpenAPI reaches Go

OpenAPI is a standard format for describing an HTTP API. A document can list paths, methods, response shapes, and security requirements. It describes an API; it does not implement the Go handler.

Zod schemadescribes data
→
ts-rest contractdescribes routes
→
OpenAPI generatorcreates a JSON document
→
Go static filesserves the generated document
  1. packages/openapi/src/index.ts builds the OpenAPI object from the contract.
  2. packages/openapi/src/gen.ts writes packages/openapi/openapi.json and apps/backend/static/openapi.json.
  3. The Go router serves static/ at /static. Its /docs handler serves static/openapi.html, which points to /static/openapi.json.

Generation is a separate gen script. The root bun dev script does not call it. Generate the document after changing the contract when you need an updated file. The documentation page loads its viewer from a network CDN, even though this study guide works offline.

Current package detail: the OpenAPI manifest points its JavaScript ./contracts export to dist/contract/index.js, while the source and compiled directory are named contracts. A consumer that uses this export can fail until the paths agree. Vite has a separate source alias.

How an email reaches Go

The email package uses React components to author an email. The backend sends email with Go. The bridge is a generated HTML file.

welcome.tsxReact email source
→
exportcreates HTML in the backend templates folder
→
Go templatefills in UserFirstName
→
Resendthe Go client sends the rendered HTML

The React template uses {{.UserFirstName}} as its default value. That text is a Go template placeholder. After export, the Go email client reads templates/emails/welcome.html, runs html/template with a data map, and sends the result through Resend.

The email dev script starts a preview. The separate export script writes files into apps/backend/templates/emails. Previewing an email does not itself export or send it. The backend's job handler can call the email client; React does not run inside the Go process.

Run the pieces

Use separate terminals. The commands below show where each command belongs. They assume the needed tools and dependencies are installed.

Terminal 1: JavaScript workspaces

# From the repository root
bun install
bun dev

Turbo starts the four workspace development tasks. Keep this terminal open.

Terminal 2: Go backend

# From the repository root
cd apps/backend
go run ./cmd/go-boilerplate

If Task is installed, task run in this directory runs the same Go command. The backend also needs its configuration and services.

Run Go from apps/backend: the current code reads paths such as static/openapi.html and templates/emails relative to its working directory. Check apps/backend/.env.sample and the Go configuration code for required settings. The server initializes the database, Redis client, and job service.

Generate files when needed

# From the repository root: writes two OpenAPI JSON files
(cd packages/openapi && bun run gen)

# From the repository root: writes backend email HTML
(cd packages/emails && bun run export)

Each line runs in its package folder and leaves your shell at the repository root. Both scripts write files. They are separate from the preview and development commands.

The frontend config reads VITE_API_URL and a Clerk publishable key when its API client is used. Values placed in frontend code can reach the browser. Keep backend secrets out of client-facing configuration; also review the process.env replacement in vite.config.ts before exposing environment values.

Read the errors you saw

Each line in the earlier output belongs to a different layer. Use the package name before the # to find the script that failed.

OutputMeaningWhat to inspect
Workspace ... not found in lockfileTurbo saw a workspace that the lockfile did not describe.Compare root workspace settings and bun.lock. Run bun install at the root after workspace changes.
wait-on: command not foundThe script tried to run a tool that was not available in its install.Check the package's devDependencies and install from the workspace root. wait-on is already declared here.
TS5102: baseUrl ... removedThe compiler being run rejected a TypeScript configuration option.Check bun.lock, the manifest's TypeScript range, and node_modules/.bin/tsc --version. In the earlier output the installed compiler was 7.0.2, while the manifests request 5.x.
cache bypassThe task ran without a cache hit. Here dev has caching disabled.This line alone is normal; look for an actual error.
Remote caching disabledTurbo is not using a remote cache.This is not the cause of the missing command or compiler error.

The lockfile and installed versions can change after an install. Check their current state rather than assuming they still match the earlier log.

If a task waits forever

Find the file in its wait-on command. Then inspect the task that should create it. For example, if the frontend waits for OpenAPI output, check the OpenAPI task and the Zod task before assuming Vite is broken.

Test yourself

Say the answer before you open it.

Does one repository mean one running program?

No. The repository contains separate programs and packages. The Go server, Vite server, and email preview have separate roles and processes.

What starts the Go server when you run bun dev?

Nothing in the current root dev setup starts it. Run the Go command separately from apps/backend.

What is the difference between an import and an HTTP request?

An import makes code available to another JavaScript package. An HTTP request sends data between running programs over a network boundary.

Does changing the Zod schema change the Go handler?

No. The TypeScript schema and the Go code are separate. Update and test both sides when their shared API changes.

Does starting the email preview export or send an email?

No. Preview, export, and send are three different actions. The Go client sends the rendered HTML after an appropriate backend action.

Why can wait-on pass even when a build has not just succeeded?

It checks for a file. A file from an earlier build can already be present.
