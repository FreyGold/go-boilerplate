Understand context.go

This guide starts with one handler and one wrapper. It then shows how this project adds a request ID, builds a request logger, and passes that logger to later code.

Read time: about 12 minutes. The examples show the intended flow. The last section states what this repository runs today.

1. Small building blocks

A handler handles one request

Echo calls a handler with an echo.Context. The handler reads or writes the HTTP request and response. It returns an error value.

func hello(c echo.Context) error {
    return c.String(200, "hello")
}

Middleware wraps a handler

A wrapper receives a handler named next. It returns a new handler. The new handler can do work before it calls next(c).

func addMessage(next echo.HandlerFunc) echo.HandlerFunc {
    return func(c echo.Context) error {
        fmt.Println("before")
        err := next(c)
        fmt.Println("after")
        return err
    }
}

wrapped := addMessage(hello)
// When Echo calls wrapped(c): before → hello → after

The returned function remembers next. Go calls this a closure. No special Echo feature is needed for that part.

Keep this model: middleware is a handler wrapper. next(c) is the point where the request moves to the next wrapper or the final handler.

2. Why the functions nest

Echo defines MiddlewareFunc as a function that takes a handler and returns a handler. EnhanceContext must return that function.

// The shape of Echo's types:
type HandlerFunc func(c echo.Context) error
type MiddlewareFunc func(next HandlerFunc) HandlerFunc

// The shape of this method:
func (ce *ContextEnhancer) EnhanceContext() echo.MiddlewareFunc {
    return func(next echo.HandlerFunc) echo.HandlerFunc {
        return func(c echo.Context) error {
            // This work runs for this request.
            return next(c)
        }
    }
}
Level 1: EnhanceContext()Returns middleware. It has access to ce.server.
Level 2: func(next ...)Receives the handler that comes next. It returns a wrapper.
Level 3: func(c ...)Runs for each request. It reads this request and calls next(c).

The outer function closes over ce. The inner function closes over next. This is why both values are available when a request arrives.

There are two return func statements because the method returns middleware, and middleware returns a handler. They do different jobs.

enhancer := NewContextEnhancer(s)  // Keep the shared server.
middleware := enhancer.EnhanceContext() // Get the wrapper function.
wrapped := middleware(hello)       // Give it the next handler.
err := wrapped(c)                  // Run it for one request.

On the next request, Echo calls wrapped again with a new request context. The wrapper reads that new request’s values.

3. The server pointer

type ContextEnhancer struct {
    server *server.Server
}

func NewContextEnhancer(s *server.Server) *ContextEnhancer {
    return &ContextEnhancer{server: s}
}

The struct keeps a pointer to the shared Server. The constructor stores that pointer once. The method uses it later to read the base logger at ce.server.Logger.

ce is just the method receiver name. It means “this ContextEnhancer.” The struct itself is not middleware. Its EnhanceContext method produces middleware.

The Server also holds config, database, Redis, and job fields. This file uses its logger field. See server.go.

4. The request ID

request_id.go reads the incoming X-Request-ID header. If the header is empty, it creates a UUID. It stores the ID in Echo’s context and sets the response header to the same value.

requestID := c.Request().Header.Get("X-Request-ID")
if requestID == "" {
    requestID = uuid.New().String()
}
c.Set("request_id", requestID)
c.Response().Header().Set("X-Request-ID", requestID)

context.go calls GetRequestID(c). That helper reads the value that the request ID middleware stored. It does not read the header itself.

What “group by request ID” means

Suppose request A creates three log events. All three can contain request_id: "A". You can search the logs for A and see those three events together.

Request A

A  auth started
A  query finished
A  response sent

Request B

B  auth started
B  response sent

The ID links log events from one request. It does not make requests share state. REST requests can remain independent.

Exact code behavior: a caller can send X-Request-ID. This code then uses that value. If the caller sends the same value again, two requests can have the same ID. A fresh ID is created only when the header is empty.

The request ID middleware must run before EnhanceContext reads the ID. If it runs later, GetRequestID(c) returns an empty string.

5. The logger chain

The base logger comes from ce.server.Logger. The code builds a logger that holds fields for this request:

contextLogger := ce.server.Logger.With().
    Str("request_id", requestID).
    Str("method", c.Request().Method).
    Str("path", c.Path()).
    Str("ip", c.RealIP()).
    Logger()
  1. With() starts a builder for a logger with extra fields.
  2. Each Str(name, value) adds one string field.
  3. Logger() finishes the logger and assigns it to contextLogger.

These calls do not write a log event. They prepare fields for events that this logger writes later.

contextLogger.Info().Msg("request complete")

// A JSON log event could contain:
// {"request_id":"A", "method":"GET", "path":"/users",
//  "ip":"203.0.113.10", "level":"info", "message":"request complete"}

Think of the base logger as a blank form. With().Str(...).Logger() fills in fields that stay on the form. Info().Msg(...) writes one event with those fields.

c.Path() gives the matched Echo route path. For a route such as /users/:id, that path is the route pattern. It is not the full request URL.

logger.go creates the base logger. It adds fields such as service and environment. It also sets the output format and destination. The request logger keeps those base settings and adds request fields.

Three names, three jobs: the package named logger has helper functions. ce.server.Logger is the shared base logger. contextLogger is the logger built for one request.

6. Trace and user fields

The New Relic transaction

if txn := newrelic.FromContext(c.Request().Context()); txn != nil {
    contextLogger = logger.WithTraceContext(contextLogger, txn)
}

newrelic.FromContext(...) looks for a New Relic transaction in the request’s Go context. txn != nil means the code found one. If it found none, this block does nothing.

Here, transaction means New Relic monitoring work. It is not a database transaction. WithTraceContext reads trace metadata and adds trace.id and span.id to the logger. It then returns the logger with those fields. See logger.go.

The user fields

if userID := ce.extractUserID(c); userID != "" {
    contextLogger = contextLogger.With().Str("user_id", userID).Logger()
}

The helper reads user_id from Echo’s context. auth.go sets that value after Clerk authentication. The code adds user_role in the same way. An empty value adds no field.

The order matters. Auth must set user data before this code reads it. If auth runs later, the logger for this request will lack those user fields. The auth middleware also writes its own events with the base logger and adds fields by hand.

7. Why store the logger?

A logger is a tool for writing events. It holds the output settings and the request fields added by With().Str(...).Logger(). It is not a list of events. No event exists until code calls Msg(...).

Could we log the request data at the end?

Yes. If you need one final event, you can call the next handler and then log with the base logger. You can read the request values at that point. You do not need to store a request logger for this case.

// Simple end-only logging. This is an alternative, not repository code.
err := next(c)
ce.server.Logger.Info().
    Str("request_id", requestID).
    Str("method", c.Request().Method).
    Msg("request finished")
return err

The current design prepares a logger with the request fields before the handler runs. Later code can write an event when work starts, when a database call fails, and when work ends. Every event gets the same request fields without adding them again.

// Example handler. This is not in the repository.
func showUser(c echo.Context) error {
    log := GetLogger(c) // Read the logger stored by the middleware.
    log.Info().Msg("start loading user")
    // Work happens here.
    log.Info().Msg("finished loading user")
    return nil
}

Both events get the same request fields. The middleware builds those fields once for this request. It does not keep adding fields across different requests. It also does not change the shared base logger.

You could store only raw values and add them to each event. That works too. The prepared logger is a shortcut for repeated events. It is not required for correctness.

Why store it in two places?

Echo’s context and Go’s request context are two separate places. The code puts the same logger pointer in both. It does this so code with either type of context can get the logger.

ObjectHow this file uses it
echo.Context, named cGives Echo code access to the HTTP request and response. c.Set and c.Get store and read values during the request.
context.Context, from c.Request().Context()Travels with the Go HTTP request. Code that receives the request context can read its values and use its cancellation signal.
 
c.Set(LoggerKey, &contextLogger)

ctx := context.WithValue(c.Request().Context(), LoggerKey, &contextLogger)
c.SetRequest(c.Request().WithContext(ctx))
  1. c.Set saves the logger in Echo’s context. GetLogger(c) reads it from there.
  2. context.WithValue makes a new Go context with the logger. It does not change the old context in place.
  3. WithContext(ctx) makes a request that uses that new context. c.SetRequest gives that request back to Echo.

An Echo handler can call GetLogger(c). A function that receives only context.Context could read the logger from the Go context. Storing it twice does not write two log events.

This is optional: if all later code uses echo.Context, one Echo value is enough. If all later code uses context.Context, one Go context value is enough. You can also pass the logger as a function argument. Echo and zerolog do not require both stores.

GetLogger(c) returns the request logger if Echo’s context holds it. Otherwise, it returns a no-op logger. A no-op logger discards events. This fallback does not use the server’s base logger.

8. One request, start to end

Assume Echo is set up so each step runs in this order. A client sends GET /users with no request ID header.

  1. 1 Request ID middleware creates ID A. It saves A in Echo’s context and in the response header.
  2. 2 Auth middleware checks the request. If auth succeeds, it sets user_id and user_role.
  3. 3 EnhanceContext reads A. It builds a logger with the request method, route path, and IP address.
  4. 4 If New Relic transaction data exists, it adds trace fields. If user data exists, it adds user fields.
  5. 5 It stores the prepared logger where later code could read it: in Echo’s context and the request’s Go context.
  6. 6 It calls next(c). The next handler could read the logger and write several events with the same request fields.

When a different request arrives, the inner function runs again. It builds a logger for that request’s values.

9. What runs in this repository today

The files define RequestID, RequireAuth, and EnhanceContext. This repository does not show code that attaches them to Echo. Its main.go prints Hello, World!.

So the request walk-through shows how these parts are meant to work together. It is not a claim that the current main.go runs them.

  • context.go: builds and stores the request logger.
  • request_id.go: chooses and stores the request ID.
  • auth.go: sets the user values after authentication.
  • logger.go: creates the base logger and adds trace fields.
  • server.go: holds the shared base logger.

10. Check your model

Try to answer each question before you open it.

Why are there two return func statements?

The first returns Echo middleware. Echo gives that function the next handler. The second returns the handler that runs for each request.

Does With().Str(...).Logger() write a log event?

No. It builds a logger with fields. A call such as Info().Msg(...) writes an event.

Do two REST requests share state when their log events have the same ID?

No. The ID is a field for finding log events. The code can reuse an ID if the caller sends the same header twice.

Is txn a database transaction?

No. This file gets it from New Relic. It supplies trace metadata.

Why store the logger twice?

c.Set makes it available to Echo code. context.WithValue makes it available through the request’s Go context.

Could this code store values and build one logger at the end?

Yes. That is enough if code needs one final event. A stored logger lets later code write events during the request without rebuilding the same fields each time. This repository does not yet use that logger.
